## Deviations from the task

- **Golden files are not pre-committed.** The task asks for a stored expected
  output compared in a test. The golden files (`tests/golden/report.json`,
  `tests/golden/summary.txt`) are generated by running the tool, which needs a
  Rust toolchain the workspace does not have. The test therefore bootstraps
  them on first run (writes them and passes) and documents the one regeneration
  command: `UPDATE_GOLDEN=1 cargo test -p lr2lc golden`. A maintainer with a
  toolchain runs that once and commits the two files; from then on the test
  compares and fails on any drift, including a renamed key. This is the only
  way to honour both "no compiler" and "CI is the proof" (a hand-written golden
  for ~60 writer fields and the full readable summary would be guesswork and
  would fail CI for the wrong reason).
- **Added a schema-key guard** (`report_keys_match_the_documented_schema`) on
  top of the golden comparison. It asserts the exact key set of the dry-run
  report and fails the moment a key is renamed, added or removed — on every
  platform, even before the golden files are committed. This satisfies the
  acceptance "the golden test fails if a key is renamed" on CI now, not only
  after the golden is committed.
- **End-to-end assertions are generic invariants, not hand-counted numbers.**
  The task lists the invariants to assert (read == converted + skipped; dry-run
  numbers == first apply numbers; second run changes nothing; checksum stable).
  These are checked dynamically from the report rather than against fixed
  counts, which is robust to fixture composition and is the tool's own output.

## Questions

- Should the golden files be generated and committed by a maintainer as part of
  the review, or should the test remain bootstrap-on-missing? The current
  design does both safely; a committed golden turns on value drift detection.
- `smart_no_longer_translatable` declaration order: noted in
  `docs/report-format.md` under Questions (the Rust field order in
  `ApplySummary` differs from the JSON key order; the key set is consistent).

## Risks / things the reviewer should look at first

- **Composition of all edges in one catalog is new territory.** Each adder is
  tested alone, but their combination in `write_full_catalog_with_files` is
  not, beyond the invariants the end-to-end test checks. If a runtime error
  appears, it is most likely here: run `cargo test -p lr2lc --test end_to_end`
  first.
- **No local compile.** Clippy (`-D warnings`) and `cargo fmt` were not run
  locally. The code mirrors existing test patterns (`apply_cli.rs`,
  `dry_run.rs`) and existing adders, but a formatting or lint nit is possible.
- **`add_iptc_combined` uses the module alias `use rights_edge as right;`**;
  `right` is not a keyword, but if a reviewer prefers `as e` for consistency,
  that is a one-line change.
- The golden schema guard asserts exact key sets; if a key is legitimately
  conditionally absent (e.g. `writer.aborted` in the applied section — not
  exercised here since the golden uses a dry run), the guard does not cover it.
  The guard is scoped to the dry-run report, where all asserted keys are always
  present.
